## 3. 前提

- 1名が順次実施する前提です。並行実施時は総工数が同じでも暦日を短縮できます。
- Docker環境が構築済みで、実施者がローカル環境を操作できます。
- 不具合修正そのものの開発工数は含まず、起票・確認・再テストだけを含みます。
- 軽微～中程度の不具合を最大8件、各1回の再テストとして見込みます。
- Chrome・Edge、PC・スマートフォン代表幅を対象とします。実機スマートフォン試験は含みません。
- メールはMailpitで確認し、外部SMTPの到達性は対象外です。
- テストデータに実在する個人・給与情報を使用しません。

## 4. 変動要因と追加見積

現時点の精度は概算で、目安は`11.5人日 ±25%`です。次の場合は追加見積とします。

- 重大不具合、DBスキーマ変更、業務フロー変更
- 対応ブラウザ・端末・OSの追加
- 本番相当インフラ、外部メール、バックアップ・復元の試験
- 性能・負荷・長時間連続運転試験
- 第三者脆弱性診断、個人情報保護監査
- 自動テスト追加実装、CI/CD構築

## 5. 推奨する実施順

1. 自動テストとヘルスチェックで基盤を確認する。
2. 正常系の初期設定から給与公開までを通す。
3. 3権限・他社・他社員のアクセス拒否を確認する。
4. CSVと入力チェックの異常系を実施する。
5. 予約時刻、重複実行、メール失敗を確認する。
6. PDF、閲覧記録、ブラウザ、レスポンシブを確認する。
7. 不具合修正後の再テストと全自動テストを実施し、結果を報告する。
