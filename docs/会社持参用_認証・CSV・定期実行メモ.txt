給与明細Webシステム 初心者向け確認メモ
作成日: 2026-08-25

注意: このメモは会社仕様寄せ実装前の学習メモです。現在の認証は /manage と /login に分離され、
/login 利用者は permission=1（一般社員）と permission=9（社員管理者）で判定します。
最新仕様は docs/deliverables/COMPANY_ALIGNMENT_IMPLEMENTATION_PLAN.md を参照してください。

============================================================
0. 最初に覚える全体像
============================================================

認証（Authentication）
  「ログインしようとしている人が誰か」を確認すること。
  主にメールアドレスとパスワードを使う。

認可・権限（Authorization）
  ログイン後、その人が「何をしてよいか」を確認すること。

Session
  ログイン中の利用者情報をサーバー側で覚えておく仕組み。

Cookie
  ブラウザ側に保存される小さな情報。
  Sessionを探すためのセッションIDなどを持つ。

Guard
  Laravelで「どのログイン受付・認証方法を使うか」を決める仕組み。

Role
  system_admin、company_admin、employeeなどの利用者権限。

Migration
  DBのテーブルやカラムをPHPコードで作成・変更するLaravelの仕組み。

CSV
  カンマ区切りのテキストファイル形式。ライブラリやメソッドの名前ではない。

Cron / Laravel Scheduler
  決めた時刻や間隔で処理を自動実行する仕組み。


============================================================
1. ログイン認証とは
============================================================

ログイン認証は、入力されたメールアドレスとパスワードから
「この人はusersテーブルの誰か」を確認する処理。

処理の基本順序:

  1. ログイン画面でメールとパスワードを入力
  2. 必須入力・メール形式を確認
  3. usersテーブルからメールが一致する利用者を検索
  4. 入力パスワードと保存済みパスワードを比較
  5. 一致すればログイン成功
  6. Sessionへログイン利用者情報を保存
  7. roleを確認し、利用可能な画面を分ける

パスワードはDBへそのまま保存しない。
ハッシュ化された値を保存し、ログイン時に一致するか確認する。

認証と権限は別物:

  認証: あなたは誰ですか？
  権限: あなたは何をしてよいですか？


============================================================
2. 社員はどうやってログインするのか
============================================================

このプロジェクトでは、次の3種類を同じusersテーブルで管理する。

  system_admin
    システム管理者。会社、会社管理者、共通テンプレートを管理。

  company_admin
    会社管理者。自社の部署、社員、給与処理を管理。

  employee
    一般社員。公開済みの本人給与明細だけ閲覧。

全員が同じ /login を使用する。
認証方法も全員同じで、メールアドレス＋パスワード。

ログイン成功後、users.roleによって表示画面・操作権限を分ける。

社員の場合はさらに次を確認する。

  ・roleがemployeeか
  ・給与明細が公開済みか
  ・給与明細のemployee_idがログイン本人のIDか

会社管理者の場合は次を確認する。

  ・roleがcompany_adminか
  ・操作対象のcompany_idがログイン中の会社と同じか


============================================================
3. 共通ログインと管理者用ログインの違い
============================================================

方式A: 全員が同じログイン画面

  /login
    system_admin
    company_admin
    employee

  ログイン後にroleで画面を分ける。
  このプロジェクトはこの方式。

方式B: 管理者と社員のログイン画面を分ける

  /manage/login
    system_admin、company_admin

  /login
    employee

  Laravelの複数Guardを使う設計が考えられる。

注意:
  システム管理者でログインした人が、自動で会社管理者や社員に
  変身するわけではない。それぞれ別アカウント・別role。

  管理者が社員本人としてログインする「代理ログイン」は別機能。
  このプロジェクトには実装されていない。


============================================================
4. Session、セッションID、Cookie
============================================================

Webの通信は、何もしなければ前回のアクセスを覚えていない。
そのため、ログイン状態を維持するためにSessionを使う。

Session:
  サーバー側に保存する。
  例: セッションID ABC123 は利用者ID 10のログイン状態。

セッションID:
  Sessionを探すためのランダムな識別番号。
  パスワードではないが、盗まれるとなりすましの危険がある。

Cookie:
  ブラウザ側に保存する。
  ブラウザはアクセスのたびにセッションIDを自動送信する。

関係:

  ブラウザのCookie
    セッションID = ABC123
          ↓
  サーバーのSession
    ABC123 = 利用者ID 10
          ↓
  Laravel
    現在のログイン利用者はID 10と判断

このプロジェクトではSessionをDBのsessionsテーブルに保存する。
設定例:

  SESSION_DRIVER=database
  SESSION_LIFETIME=120

ログアウト時はサーバー側Sessionを無効にする。
古いセッションIDを送ってもログイン状態には戻れない。

「ログイン状態を保持する」は通常Sessionとは別に、
長期間ログインを復元するCookieを使用する機能。


============================================================
5. Guardとは
============================================================

GuardはLaravelの「ログイン受付窓口」。

現在のプロジェクト:

  Guard名: web
  driver: session
  provider: users

意味:

  webというログイン受付を使う。
  ログイン状態はSessionで管理する。
  利用者はUser Modelを使ってusersテーブルから探す。

GuardとRoleの違い:

  Guard
    どのログイン受付・認証方法を使ったか。

  Role
    ログイン後、何を操作してよいか。

現在は1つのweb Guardを3権限で共用する。

  web Guard
    ├ system_admin
    ├ company_admin
    └ employee

複数Guardの例:

  manage Guard
    管理者ログイン用

  employee Guard
    社員ログイン用

ルートでは次のように指定できる。

  auth:manage
    manage Guardでログイン済みか確認

  auth:employee
    employee Guardでログイン済みか確認

Guardを分けてもroleやcompany_idの確認は必要。


============================================================
6. Auth::attempt()の意味
============================================================

コード:

  Auth::attempt(
      $credentials,
      $request->boolean('remember')
  );

日本語:

  メールアドレスとパスワードでログインを試す。
  rememberがtrueなら、ログイン状態を長期間保持する。

記号:

  $
    PHPの変数を表す。

  ::
    クラスの機能を呼び出す。

  ->
    変数に入っているオブジェクトの機能を呼び出す。

  ()
    メソッドへ渡す値を書く。

  ,
    渡す値を区切る。

  ;
    PHP命令の終了。

$credentialsの例:

  email = yamada@example.com
  password = Password123

$request->boolean('remember'):

  チェックあり  → true
  チェックなし  → false

Auth::attempt()の内部処理:

  1. デフォルトのweb Guardを選択
  2. users Providerからメールを検索
  3. パスワードを比較
  4. 成功時はSessionへ利用者情報を保存
  5. remember=trueなら長期ログイン用Cookieを作成
  6. 成功はtrue、失敗はfalseを返す


============================================================
7. Migrationとは
============================================================

MigrationはDBのテーブル・カラムをPHPコードで管理するLaravel機能。

Migration  = DB構造を作る
Seeder     = 初期データを入れる
Model      = PHPからテーブルを操作する

新しいテーブルを作る例:

  php artisan make:migration create_announcements_table

作成されるファイル例:

  database/migrations/
  2026_08_25_123456_create_announcements_table.php

主な記載:

  Schema::create('announcements', ...)
    announcementsテーブルを作る。

  $table->id()
    連番IDを作る。

  $table->string('title')
    titleという短い文字列カラムを作る。

  $table->text('body')
    bodyという長文カラムを作る。

  $table->timestamps()
    created_at、updated_atを作る。

既存usersテーブルにphoneを追加する例:

  php artisan make:migration add_phone_to_users_table --table=users

up()の例:

  Schema::table('users', function (Blueprint $table) {
      $table->string('phone', 30)->nullable();
  });

down()の例:

  Schema::table('users', function (Blueprint $table) {
      $table->dropColumn('phone');
  });

up():
  変更を進める。テーブル・カラム追加。

down():
  変更を戻す。テーブル・カラム削除。

実行:

  php artisan migrate

状態確認:

  php artisan migrate:status

注意:
  migrate:rollback、migrate:freshはデータ削除につながる可能性がある。
  本番で安易に実行しない。
  実行済みMigrationを直接変更せず、新しいMigrationを追加する。


============================================================
8. CSVとは・外部ライブラリとは
============================================================

CSVはファイル形式。

例:

  employee_number,name,email
  E001,山田太郎,yamada@example.com

CSVそのものはライブラリでもメソッドでもない。

PHP標準機能:

  fgetcsv()
    CSVを1行読む。

  fputcsv()
    CSVを1行書く。

このプロジェクト:

  外部CSVライブラリは未使用。
  PHP標準のfgetcsv()と独自CsvReaderを使用。

  CsvReader
    文字コード判定、UTF-8変換、見出し・行読込を担当。

  PayrollCsvImporter
    社員確認、必須項目、金額確認、合計計算、DB登録を担当。

代表的な外部ライブラリ:

  League CSV
    CSV専用。CSVを扱いやすくするPHPライブラリ。

  Laravel Excel
    CSVに加えてExcelの.xlsxも扱えるLaravel向けライブラリ。

選び方:

  CSVだけ              → League CSV
  Excelも必要          → Laravel Excel
  小規模なCSVだけ      → PHP標準fgetcsv()でも可能

外部ライブラリを使っても、次の業務チェックは自分で作る。

  ・社員番号が存在するか
  ・自社社員か
  ・必須項目があるか
  ・金額が数値か
  ・総支給、控除、差引の計算
  ・公開済みデータを変更させない


============================================================
9. Cron・Laravel Schedulerとは
============================================================

Cron（クーロン）は、指定時刻・間隔で処理を起動する仕組み。
PHPのメソッドやCSVのようなファイル形式ではない。

LaravelではLaravel Schedulerを使ってスケジュールを記載できる。

毎日9時の例:

  Schedule::command('payslips:send-mail')
      ->dailyAt('09:00')
      ->timezone('Asia/Tokyo')
      ->withoutOverlapping();

意味:

  command()
    実行するArtisanコマンドを指定。

  dailyAt('09:00')
    毎日9時に実行。

  timezone('Asia/Tokyo')
    日本時間を使用。

  withoutOverlapping()
    前回処理中なら重複実行しない。

会社管理者が画面で日時を指定する場合:

  例: 2026-08-31 09:00をscheduled_forへ保存。

Scheduler側:

  Schedule::command('payslips:publish-scheduled')
      ->everyMinute()
      ->withoutOverlapping();

毎分、次を検索する。

  status = scheduled
  scheduled_for <= 現在時刻

対象があれば:

  1. statusをpublishedへ変更
  2. published_atを保存
  3. 社員ごとにメール送信
  4. 成功した明細にnotified_atを保存

毎分確認のため、指定時刻から最大約1分遅れる可能性がある。


============================================================
10. テスト仕様書へ落とす基本観点
============================================================

どの処理でも次を確認する。

  1. 正しい入力で成功するか
  2. 必須項目が空なら拒否するか
  3. 不正形式なら拒否するか
  4. 権限が違えば拒否するか
  5. 他社・他人のデータを拒否するか
  6. 状態が違えば拒否するか
  7. 成功時にDBが正しく更新されるか
  8. 失敗時に途中データが残らないか
  9. 画面・メール・PDFの出力が正しいか
 10. 重複実行しても二重登録・二重送信しないか

ログイン:

  ・正しいメール・パスワード
  ・誤ったパスワード
  ・存在しないメール
  ・利用停止利用者
  ・利用停止会社
  ・ログアウト後のアクセス
  ・rememberあり／なし
  ・Session期限切れ

Guard・権限:

  ・管理者が管理画面へ入れる
  ・社員が管理画面へ入れない
  ・A社管理者がB社データを見られない
  ・社員Aが社員Bの明細を見られない

CSV:

  ・正常CSV
  ・必須列不足
  ・空ファイル
  ・存在しない社員番号
  ・金額が文字
  ・UTF-8／Shift_JIS
  ・途中エラー時に全体を反映しない

Scheduler・メール:

  ・公開時刻前は送信しない
  ・公開時刻後は送信する
  ・draftは送信しない
  ・publishedを再送信しない
  ・メール成功時にnotified_atを保存
  ・メール失敗時の状態とログ
  ・同時実行でも二重送信しない
  ・日本時間で正しく動く


============================================================
11. 会社で確認したい質問
============================================================

認証:

  □ ログイン画面は全権限共通か、管理者用と社員用で分かれているか
  □ Guardはいくつ定義されているか
  □ usersテーブルは共通か、管理者・社員で別テーブルか
  □ Roleはどこで管理しているか
  □ Sessionの保存先と有効時間は何か
  □ ログイン状態保持Cookieを使用しているか
  □ 管理者の代理ログイン機能があるか

Migration:

  □ 実行済みMigrationを変更しない運用になっているか
  □ Migrationの実行担当・実行手順は決まっているか
  □ 本番DBのバックアップ・ロールバック手順はあるか

CSV:

  □ 使用している外部ライブラリ名は何か
  □ composer.jsonにleague/csv、maatwebsite/excelなどがあるか
  □ CSVだけか、Excelの.xlsxも対象か
  □ 文字コード、最大件数、最大容量は何か
  □ 途中行エラー時は全件取消か、正常行だけ登録か

Scheduler・メール:

  □ OSのCronか、Laravel Schedulerか
  □ schedule:runかschedule:workのどちらを使っているか
  □ 実行間隔とタイムゾーンは何か
  □ メール失敗時に自動再送するか
  □ 二重実行防止はあるか
  □ 送信結果をどのテーブル・ログへ記録するか
